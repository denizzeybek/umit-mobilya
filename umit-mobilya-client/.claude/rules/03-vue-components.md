# Rule 03 — Vue components

> Half of this codebase's conventions are already enforced by ESLint. The other half is why this file exists.

## Why this rule exists

Two systems here behave in ways that surprise people who assume a normal Vue
setup. Components under `src/components/ui/global/` are registered globally with
an `F` prefix by `plugins/globalComponents.ts` (`import.meta.glob`, eager), so
importing them explicitly is redundant and misleading. And `components.d.ts` is
regenerated by `unplugin-vue-components` on every build — it carries
`/* eslint-disable */` and `// @ts-nocheck` at the top precisely because nothing
should treat it as source.

Section ordering inside `<script setup>` is a house convention recorded in
`notes.md`. It is not enforced by a linter, so it only survives if you follow it.

## Do

1. Order `<script setup>` exactly as `notes.md` prescribes:
   imports → `IProps`/`defineProps` → `IEmits`/`defineEmits` → composables &
   stores → `ref` → `computed` → functions → `watch` → `onMounted`.
2. Put feature code under `src/views/<feature>/` using the existing split:
   `_views/` (route components), `_components/`, `_modals/`, `_etc/`.
3. Drop new shared widgets into `src/components/ui/global/` and reference them as
   `<FYourComponent>` — no import statement.
4. Register a PrimeVue component in `src/plugins/primeVue/primeVue.ts` when it
   fails to resolve at runtime; the auto-import resolver is not always enough
   here.
5. Use `useFToast()` from `@/composables/useFToast` for all toasts.
6. Import through the `@` alias, except for siblings inside the same feature
   folder, which the codebase references relatively.
7. Bind form fields by passing `name` to an `F*` input. They wire themselves via
   `useField(() => props.name)` — that prop is the entire wiring.

## Don't

- ❌ Import anything from `components/ui/global/` explicitly.
- ❌ Hand-edit `components.d.ts`. It is generated, committed, and denied in
  `.claude/settings.json`.
- ❌ Call vue-toastification's `useToast()` directly.
- ❌ Add `v-model` on top of an `F*` input that already has `name`.
- ❌ Invent new folder names under a feature. Use the four that exist.
- ❌ Hardcode a hex colour. Tokens live in `src/constants/colors.ts` and are
  `f-`-prefixed (`f-primary`, `f-stroke`); `tailwind.config.js` spreads them into
  `colors`, `textColor` and `borderColor`.

## Enforced by ESLint — don't fight it

`eslint.config.js` will fail the build on these, so write them right the first
time:

- `vue/block-order` — `template` → `script` → `style`
- `vue/component-api-style` — `<script setup>` only, no Options API components
- `vue/define-macros-order` — `defineProps` → `defineEmits` → `defineSlots` →
  `defineOptions`, with `defineExpose` last
- `vue/attributes-order` — directives before plain attributes before events
- `@typescript-eslint/no-unused-vars` — prefix with `_` if genuinely unused

## The modal pattern

All five modals in `_modals/` already follow one shape. Copy it rather than
inventing a variant:

```vue
<!-- Parent -->
<CategoryModal v-if="showModal" v-model:open="showModal" @fetchCategories="fetch" />
```

```ts
// Modal
const open = defineModel<boolean>('open');
const isEditing = computed(() => !!props.data);

onMounted(() => resetForm({ values: getInitialFormData.value }));

const handleClose = () => {
  resetForm();
  open.value = false;
};
```

The parent's `v-if` is load-bearing: it forces a remount so `onMounted` re-seeds
the form. After a successful write the modal emits (`fetchCategories`,
`fetchProducts`) so the parent refetches — it never mutates the parent's list.
